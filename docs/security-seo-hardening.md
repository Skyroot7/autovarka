# Проверка безопасности, SEO и производительности

Ветка `security/seo-hardening-2026-11` основана на `af793a5`. Промежуточный коммит `e06d4f2` сохраняет 43 восстановленных файла до завершения тестов.

## Безопасность

- POST аналитики и видео проверяет сессию до чтения тела. Некорректные поля отклоняются до записи. GA4 и GTM принимают только идентификаторы, которые сериализуются как данные.
- AnalyticsLoader получает публичные настройки на сервере. Валидированные настройки кешируются отдельно от коммерческих данных, сессий и заказов. После сохранения соответствующий тег кеша аннулируется.
- Blob actions требуют сессию. Загрузка принимает декодируемые JPEG, PNG, WebP и GIF до 4 МиБ. Проверяются фактический формат, размер и ограничения растра. Оригинальные байты сохраняют качество и анимацию. При удалении проверяются имя и канонический URL файла через настроенное хранилище и используется условное удаление с ETag.
- Редактор отдельно сохраняет пять наборов названий и описаний. Удаление изображения из черновика меняет привязку после сохранения карточки. Объект Blob остаётся доступным для других карточек и при отмене формы.
- В production и Preview вход требует `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` и `ADMIN_PASSWORD_SALT`. Хеш вычисляется прежним PBKDF2 SHA-512, 100 000 итераций и 64 байта. Ошибка конфигурации приводит к 503 без создания сессии.
- Запись, расчёт и оформление заказов находятся вне этого изменения. Проверка цен на сервере, идемпотентность, атомарное хранение заказов и ограничение частоты входа остаются отдельными задачами.

## SEO

Сохранены self-canonical, украинские пути без префикса, пять hreflang и украинский x-default. HTML служебных страниц доступен роботу для чтения noindex, API закрыты в robots.txt. Sitemap содержит только публичные страницы. В локальном каталоге из 10 товаров проверены 70 URL sitemap и 50 карточек.

Карточки и публичные разделы получают отдельные метаданные и полные OG/Twitter. Размер баннера указан как 1200×400. Неизвестные размеры фотографий товаров опущены. Product, Offer и BreadcrumbList сохраняют ссылки, SKU, цену, валюту, наличие и изображения. Удалены выдуманные MPN, срок действия цены, универсальная категория и неподтверждённые поля доставки и гарантии. Удалены разметка невидимого FAQ и ссылка SearchAction на отсутствующий поиск.

Главная помогает выбирать напряжение, подключение и объём. Каталог остаётся страницей сравнения наличия, ассортимента и цен. Поэтому каталог может лучше отвечать на запросы «купить» или «цена». Подтвердить распределение запросов между страницами можно в отчёте Google Search Console по запросам и URL. Данных Search Console для этого этапа не было.

## Проверка Vercel Preview

1. Проверьте, что для Preview этой ветки подключены отдельные Upstash и Blob. Заполните тестовый каталог без данных покупателей. Убедитесь, что настройки Production не наследуются Preview-окружением.
2. Для входа задайте отдельные `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`, `ADMIN_PASSWORD_SALT` в Preview. Сверьте наличие обязательных переменных Production перед будущим релизом без чтения или вывода их значений.
3. Для проверки тегов используйте тестовые идентификаторы GA4/GTM. Поле принимает только идентификатор, без скрипта. Старые значения, не соответствующие формату GA4/GTM, требуют отдельной проверки перед релизом. Фактические значения production не проверялись.
4. Пройдите пять языков. Сверьте canonical, hreflang, robots, sitemap и видимость товаров без JS. В Preview canonical ожидаемо указывает на основной домен. Проверьте карточки с наличием и без него, цену, галерею и сохранение количества в корзине. Форму оформления проверьте до отправки.
5. В новом контексте браузера проверьте 401 для записи настроек без входа. После входа сохраните тестовые настройки и проверьте их появление после обновления страницы. Проверьте загрузку тестового файла до 4 МиБ и отклонение неподдерживаемого формата.
6. Сравните несколько одинаковых мобильных запусков Lighthouse с текущей версией. Проверьте загрузку фото на мобильном экране и ошибки Vercel Functions. Полевые данные подтверждаются отдельно после накопления выборки.

## Повтор локальных проверок

В одном терминале запустите `node tests/fixtures/admin-kv-server.mjs`. Эта заглушка принимает записи только в память и отклоняет команды по заказам.

Во втором терминале используйте локальную production-сборку с тестовыми привязками:

```bash
npm run build
ADMIN_USERNAME=fixture-admin ADMIN_PASSWORD_SALT=fixture-only-salt \
ADMIN_PASSWORD_HASH=$(node -e 'process.stdout.write(require("node:crypto").pbkdf2Sync("fixture-only-password","fixture-only-salt",100000,64,"sha512").toString("hex"))') \
KV_REST_API_URL=http://127.0.0.1:3601 KV_REST_API_TOKEN=fixture-only \
BLOB_READ_WRITE_TOKEN='' npm start -- --hostname localhost --port 3600
```

С Chromium и установленным Playwright Core запустите `node tests/hardening-browser.mjs` и `BASE_URL=http://localhost:3600 npm run test:browser`. При внешней установке Playwright Core задайте `PLAYWRIGHT_MODULE_PATH` до его `index.mjs`. Эти команды предназначены для локальной сборки на указанной заглушке.
